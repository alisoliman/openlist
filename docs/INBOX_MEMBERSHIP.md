# Inbox selection and unfiled content

Inbox is an ordered selection of existing task IDs. Add to Inbox (⇧⌘I) and Remove from Inbox (⇧⌘R) only change selection. Titles, notes, labels, attachments, parents, document order and owning list remain the same. Tasks can be selected from any active list, including nested tasks. Repeated Add does not create a copy or move an existing selection. Removing an unfiled task leaves it reachable in Tasks and the Unfiled content tab.

The Unfiled content tab retains the original rich Inbox document: its UUID, summary, non-task blocks, collapsed branches, nested tasks and completed content. “Move to List → Unfiled content” is an ownership operation and still moves the complete subtree. Review unfiled sorts the original capture document into lists; it does not remove queue membership. New unfiled task captures, including task conversion and nested capture, enter the queue. Independent duplicate, template and fragment copies start outside it, even when a copy keeps schedules.

The queue has saved manual order, independent of document sort order. Drag onto another queue task to place it before that task; the task's Inbox actions menu also has keyboard/VoiceOver-accessible Move earlier and Move later commands. Sidebar, menu and widget show the same open-member count. Completed members can remain visible using the Inbox completed-visibility preference; they do not count as open. Archived or temporarily missing sources are hidden without losing selection, and unarchive makes selected tasks visible again. Deleting a task removes its membership with the task.

Ordinary completion retains selection. Reopening carries selection to its new calendar occurrence. Completing a repeating occurrence clears its selection and the selection of subtasks reset for the next occurrence. The next occurrence requires an explicit Add. The payload is bound to an occurrence ID, so an old client advancing a repeat without clearing the field cannot make the new occurrence silently rejoin. Completion Undo restores the previous occurrence and selection; a later deliberate selection edit is not overwritten. Editor deletion Undo restores the original membership with the original task identity. Membership Undo changes only membership and refuses to overwrite a newer different selection. When completion Undo or ordinary reopen rebinds the same decision to a different calendar occurrence, native membership Undo/Redo preserves that decision identity and uses the task’s actual occurrence.

## Storage and migration

`Block.inboxMembershipData` is one optional Data attribute containing a versioned JSON value: version, included decision, finite manual order, selected occurrence ID and an optional explicit-decision UUID. Explicit Remove has a fresh decision UUID even when recurrence already cleared the selection; this lets completion Undo preserve that later choice. Automatic exclusions and legacy defaults remain stable. The new initializer explicitly writes an excluded value. Existing SQLite/CloudKit records have nil, with no dynamic migration default.

Bootstrap and system-record sync reconciliation classify only nil task records with a resolved owner. Legacy tasks in the original system Inbox become selected in stable outline order, including nested and completed tasks. Legacy tasks in other known lists become explicitly excluded. A missing owner or unresolved alias waits for a later import. Non-task rich content is not classified. Removing selection writes an explicit excluded value, never nil, so later bootstrap or sync cannot reseed a removed task. Unknown versions and unreadable payloads remain byte-for-byte intact, are not classified, and show recovery guidance in Inbox. A compatible version or a chosen backup can recover them; this app never guesses a replacement.

Membership and reorder actions read their targets before mutation, commit once, and register Undo only after a successful save. Failed saves restore only the changed selection fields, preserving unrelated retryable editor drafts. The normal save error path remains responsible for other uncommitted edits. Missing targets/owners or unknown payloads fail without changing selection. Migration changes remain retryable if the normal bootstrap save fails. Membership does not create extra activity-history events.

## Backup and release validation

Logical backup format **2** includes the optional field for every block, including excluded, archived and unknown future payloads. Version 1 packages explicitly upgrade in memory with nil membership, then use the same ownership-aware migration when the restored library starts. Version 2 prevents older readers from accepting a backup and silently dropping curation. The library identity and every existing task UUID remain unchanged by migration or full restore. A restore already queued by the version 1 app is rejected before reading or selecting its older staged store. The startup error offers Cancel pending restore; selecting the original version 1 backup again performs the supported logical upgrade. Original and staged files remain intact. A library already restored before the upgrade can still return to its retained original: startup recognizes the exact previous schema, copies the closed original through Core Data with read-only source options, and lets a CloudKit-disabled SwiftData container migrate only that private copy for validation. Original database, WAL and external media stay unchanged during preflight. After selection commits, the normal app factory migrates the selected original. Newer or unrelated schemas are rejected with recovery guidance.

The focused Inbox runner writes a real SQLite library in a separate executable compiled with the frozen pre-change Block schema. A new process opens the current schema, verifies old rows are still nil before bootstrap, migrates, removes and reorders tasks, and reopens again. It checks recurrence, completion/editor/membership Undo, real read-only save failure, retained live values, first fetch and saved state. Backup checks exercise format 2 field coverage and version 1 staging/reopen. Offline sync/schema checks require the new attribute to be optional and all CloudKit schema constraints to continue passing.

No live CloudKit account or user library is used by these checks. Before a production release, follow CONTRIBUTING's signed disposable two-Mac CloudKit gate and additive production-schema promotion: validate old-client/new-client record imports, nil classification, explicit exclusion after another device removes a task, and concurrent whole-payload selection changes. CloudKit resolves the single field using its existing record conflict behavior; this release does not claim a collaborative multi-writer ordering protocol.
